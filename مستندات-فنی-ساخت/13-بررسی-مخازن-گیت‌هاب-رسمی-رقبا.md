# بررسی مخازن گیت‌هاب رسمی رقبا — شواهد مستقیم کد

**پروژه:** دلی (DALI) — پلتفرم جامع خدمات و تجربه گردشگری + شبکه تاکسی گردشگری
**تاریخ تدوین:** ۱۴۰۵/۰۶/۱۰ (۱ سپتامبر ۲۰۲۶) — به‌روزرسانی ۱۴۰۵/۰۶/۱۱ با بررسی Booking.com و TripAdvisor
**هدف سند:** برخلاف اسناد ۱۱ و ۱۲ که بر پایه‌ی آگهی‌های استخدام و گزارش حوادث بود، این سند مستقیماً سازمان‌های رسمی گیت‌هاب متعلق به رقبا را بررسی می‌کند — شواهد نزدیک‌تر به کد واقعی، نه فقط استنباط از آگهی شغلی. پوشش: Eghamat24، Alibaba.ir، Snapp (ایرانی) و Booking.com، TripAdvisor (بین‌المللی).

---

## ۱. Eghamat24 — `github.com/eghamat24`

**ریپوهای شناسایی‌شده:** `vue3-starter-template`، `react-starter-template`، `database-repository`

**یافته:** اقامت۲۴ هم‌زمان از **Vue.js 3** و **React** استفاده می‌کند — به‌احتمال زیاد تیم‌ها یا محصولات مختلف داخل همان شرکت، هرکدام با استارتر تمپلیت اختصاصی خودشان. وجود یک ریپوی مجزا (`database-repository`) نشان می‌دهد چند سرویس/تیم از یک اسکیمای دیتابیس مشترک با مدیریت migration متمرکز استفاده می‌کنند.

---

## ۲. Alibaba.ir — `github.com/alibaba-aero` (۲۶ ریپو)

**یافته‌ها:**
- کامپوننت **Vue.js** (آیکون SVG با Font Awesome)
- **React Native** — پیاده‌سازی سفارشی و پرکارایی ScrollView برای iOS/Android (نشان‌دهنده‌ی سرمایه‌گذاری فنی روی تجربه‌ی موبایل، نه فقط استفاده از کتابخانه‌ی آماده)
- مخزن سوالات مصاحبه‌ی فنی داخلی شرکت

**تأیید متقاطع:** این یافته با آگهی استخدام رسمی علی‌بابا (بک‌اند ASP.NET، فرانت React/Android-Java/iOS) که در [سند ۱۱](11-بررسی-تکنولوژی-رقبا-و-چالش‌های-فنی.md) آمده بود هم‌خوانی دارد — علی‌بابا بک‌اند .NET و فرانت جاوااسکریپتی مدرن (Vue + React Native) دارد.

## ۳. Snapp — `github.com/snapp-cab` + `github.com/snapp-incubator` (۱۱۱ ریپو) — مهم‌ترین یافته

سطح مهندسی زیرساخت اسنپ در این سازمان کاملاً آشکار می‌شود:

| ریپو | کارکرد | اهمیت |
|---|---|---|
| **chaos-operator** | عملگر Kubernetes برای Chaos Engineering | تزریق عمدی خطا روی سیستم زنده برای تست مقاومت — تکنیکی که فقط شرکت‌های خیلی بالغ به‌کار می‌برند |
| **argocd-complementary-operator** | تکمیل‌کننده‌ی ArgoCD | تأیید استفاده از **GitOps کامل** برای دیپلوی (نه دیپلوی دستی) |
| **age-operator** | مدیریت اسرار (secrets) با ابزار رمزنگاری `age`، به‌صورت GitOps | پاسخ دقیق به توصیه‌ی کلی «مدیریت اسرار» در [سند ۱۲](12-حوادث-امنیتی-واقعی-و-درس‌های-هاردنینگ.md) — اسنپ دقیقاً از `age`/SOPS استفاده می‌کند، نه Vault سنگین |
| **S3 Operator** (روی Ceph RGW) | مدیریت Object Storage خودمیزبان | نشان می‌دهد اسنپ حداقل بخشی از زیرساخت را خودمیزبان (self-hosted)، نه صرفاً ابر عمومی، اداره می‌کند |
| **Koordinator** | زمان‌بندی پیشرفته‌ی workload برای میکروسرویس/big-data/AI | مقیاس عملیات فراتر از یک سرویس ساده است |
| **MQTT/NATS broker tools (Go)** | ابزار مانیتورینگ پیام‌رسانی | تأیید مجدد استفاده از NATS/message broker که در [سند ۰۱](01-تحلیل-الگوهای-موفق-و-ناموفق.md) پیش‌تر ذکر شده بود |

**نتیجه‌گیری کلیدی:** اسنپ نه‌فقط کاربر Kubernetes است، بلکه **عملگرهای سفارشی (custom operators)** برای خودش می‌سازد. این سطح از بلوغ مهندسی زیرساخت فراتر از چیزی است که یک تیم کوچک MVP بتواند از روز اول بسازد، اما جهت‌گیری صحیح (GitOps + مدیریت اسرار سبک از پایه) را نشان می‌دهد.

## ۴. Booking.com — `github.com/bookingcom`

| ریپو | کارکرد | اهمیت |
|---|---|---|
| **rules_booking / bazel-central-registry** | قوانین سفارشی **Bazel** (سیستم بیلد گوگل برای مونوریپوهای غول‌پیکر) | Booking.com کل کدبیس چندزبانه‌اش را در یک مونوریپوی واحد با Bazel می‌سازد — سطحی از پیچیدگی مهندسی مخصوص شرکت‌های خیلی بزرگ |
| **shipper** | ابزار خودساخته برای **canary / blue-green deployment چندکلاستری** روی Kubernetes با Helm | نسخه‌ی جدید ابتدا فقط روی درصد کمی از سرورها (canary) اجرا می‌شود؛ در صورت نبود مشکل، به‌تدریج گسترش می‌یابد — تکنیک حیاتی برای پلتفرمی با میلیون‌ها کاربر که نمی‌تواند ریسک یک دیپلوی بد را تحمل کند |
| **perfsuite-ios** | کتابخانه‌ی Swift برای پایش عملکرد اپ iOS | تأیید توسعه‌ی اپ iOS نیتیو با سرمایه‌گذاری اختصاصی روی متریک‌های performance |
| **carbonapi** | مرتبط با Graphite/Carbon (سیستم متریک و مانیتورینگ) | زیرساخت مانیتورینگ اختصاصی، نه فقط استفاده از ابزار آماده |

**نتیجه‌گیری:** Booking.com مقیاس مهندسی کاملاً متفاوتی دارد — مونوریپوی Bazel و ابزار canary-deployment خودساخته، سطحی که فقط شرکت‌های چندهزارنفره به آن می‌رسند. این الگو **مستقیماً برای دلی قابل‌اجرا نیست** (فراتر از نیاز فازهای ۱ تا ۴ دلی)، اما جهت‌گیری بلندمدت را نشان می‌دهد: اگر دلی روزی به مقیاس ملی برسد، canary deployment (نه دیپلوی یکجا برای همه‌ی کاربران) باید در نقشه راه فاز ۴/۵ لحاظ شود.

## ۵. TripAdvisor — `github.com/tripadvisor`

| ریپو | کارکرد | اهمیت |
|---|---|---|
| **elasticsearch-remove-token-filter** | پلاگین سفارشی Elasticsearch برای حذف کامل stop-wordها (نه فقط حذف کلمه، بلکه حذف موقعیتشان در متن) | تأیید می‌کند **Elasticsearch** موتور جست‌وجوی اصلی TripAdvisor برای نظرات/هتل‌هاست |
| مثال چندزبانه در مستندات پلاگین | نمونه: حذف صحیح کلمات ربط فرانسوی («de»، «la») در عبارت «Hotels pres de la tour eiffel» | این پلاگین دقیقاً برای **جست‌وجوی چندزبانه‌ی دقیق** ساخته شده |
| **android-clockseekbar** | ویجت اندروید برای انتخاب زمان | تأیید توسعه‌ی اپ اندروید نیتیو |

**نتیجه‌گیری کلیدی و مرتبط‌ترین یافته برای دلی:** TripAdvisor برای پشتیبانی درست از جست‌وجوی چندزبانه، مجبور شده رفتار پیش‌فرض Elasticsearch را سفارشی‌سازی کند. **این دقیقاً همان مشکلی است که دلی در فاز ۵ (گردشگر خارجی) با آن روبه‌رو خواهد شد** — اگر جست‌وجوی مقصد/هتل چندزبانه (فارسی + انگلیسی + عربی برای زائر خارجی) ساخته شود، نمی‌توان به رفتار پیش‌فرض موتور جست‌وجو تکیه کرد؛ باید از همان فاز طراحی، تست چندزبانه لحاظ شود.

## ۶. به‌روزرسانی معماری فنی دلی — ابزار مشخص مدیریت اسرار

بر پایه‌ی یافته‌ی `age-operator` اسنپ، توصیه‌ی کلی «مدیریت اسرار با Vault/env» در [سند ۱۰](10-معماری-فنی-MVP.md) اکنون دقیق‌تر می‌شود: برای یک تیم کوچک در فاز ۱، **SOPS + age** مسیر عملی‌تری نسبت به Vault سنگین است — سبک‌تر، GitOps-friendly، و دقیقاً همان ابزاری که اسنپ در مقیاس بزرگ استفاده می‌کند. Vault می‌تواند در فازهای بعدی (توسعه چندشهری، فاز ۴) در صورت نیاز به مدیریت متمرکزتر اسرار جایگزین شود.
