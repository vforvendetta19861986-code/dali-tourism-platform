# معماری لایه‌ای و ارتباط سرویس‌ها — تحلیل عمیق

**پروژه:** دلی (DALI) — پلتفرم جامع خدمات و تجربه گردشگری + شبکه تاکسی گردشگری
**تاریخ تدوین:** ۱۴۰۵/۰۶/۱۱ (۲ سپتامبر ۲۰۲۶)
**هدف سند:** تحلیل عمیق اینکه پلتفرم‌های نمونه (اسنپ، علی‌بابا، Booking.com و مشابه) در چه لایه‌هایی کار می‌کنند، چطور سرویس‌ها با هم و با APIهای بیرونی ارتباط برقرار می‌کنند، و کد نرم‌افزار در عمل چگونه جریان دارد. این سند مکمل [سند ۱۰- معماری فنی MVP](10-معماری-فنی-MVP.md) است و جزئیات لایه‌بندی و پروتکل ارتباطی آن را باز می‌کند.

## ۱. معماری لایه‌ای استاندارد این نوع پلتفرم‌ها

```
┌─────────────────────────────────────────────────────────────┐
│  لایه ۱: کلاینت (Client Layer)                                │
│  اپ مسافر، اپ راننده، پنل وب مدیریت، پنل B2B عرضه‌کننده        │
└───────────────────────────┬─────────────────────────────────┘
                             │ HTTPS/REST یا GraphQL (پروتکل عمومی)
┌───────────────────────────▼─────────────────────────────────┐
│  لایه ۲: API Gateway                                          │
│  (Nginx / Kong / Envoy) — نقطه‌ی ورود واحد                    │
│  احراز هویت، Rate Limiting، مسیریابی درخواست به سرویس درست     │
└───────────────────────────┬─────────────────────────────────┘
                             │ gRPC (ارتباط داخلی، سریع و سبک)
        ┌────────────────┬──┴───────────────┬────────────────┐
        │                │                  │                │
┌───────▼──────┐ ┌───────▼──────┐  ┌────────▼───────┐ ┌──────▼───────┐
│سرویس دیسپچ    │ │سرویس رزرو    │  │سرویس پرداخت    │ │سرویس عرضه‌کننده│
│(Rides/        │ │(Bookings:    │  │(Payments/      │ │(Supplier/     │
│Dispatch)      │ │Hotel/Tour/   │  │Wallet)         │ │Admin)         │
│real-time      │ │Restaurant)   │  │                │ │               │
└───────┬───────┘ └───────┬──────┘  └────────┬───────┘ └──────┬───────┘
        │                 │                  │                │
        └────────┬────────┴──────────┬───────┴────────────────┘
                  │ صف پیام (Kafka/NATS/RabbitMQ) — رویدادهای async
                  │ مثل: «سفر تمام شد» → به‌روزرسانی کیف‌پول + گزارش
┌─────────────────▼─────────────────────────────────────────────┐
│  لایه ۳: داده (Data Layer)                                     │
│  PostgreSQL (تراکنش‌های اصلی) + Redis (کش، geo-query، صف کوتاه) │
└─────────────────────────────────────────────────────────────────┘
                  │
┌─────────────────▼─────────────────────────────────────────────┐
│  لایه ۴: یکپارچه‌سازی با بیرون (Integration Layer)               │
│  درگاه پرداخت (زرین‌پال) | نقشه (نشان) | پیامک | GDS/بلیط (ریسلر)│
└───────────────────────────────────────────────────────────────┘
```

این لایه‌بندی، ترکیبی است از الگوهای صنعتی استاندارد سیستم‌های ride-hailing/OTA و شواهد مستقیمی که در [سند ۱۱](11-بررسی-تکنولوژی-رقبا-و-چالش‌های-فنی.md) و [سند ۱۳](13-بررسی-مخازن-گیت‌هاب-رسمی-رقبا.md) از رقبای واقعی جمع‌آوری شد.

## ۲. چرا سه پروتکل مختلف در سه جای مختلف؟

| مسیر ارتباط | پروتکل | چرا |
|---|---|---|
| اپ موبایل ↔ API Gateway | **REST (HTTP/JSON)** یا گاهی GraphQL | کلاینت‌های موبایل و مرورگر فقط HTTP را به‌راحتی می‌فهمند؛ این پروتکل عمومی و استاندارد صنعتی است |
| سرویس ↔ سرویس (داخلی) | **gRPC** | سبک‌تر و سریع‌تر از REST/JSON چون از Protocol Buffers (باینری) استفاده می‌کند؛ برای هزاران درخواست داخلی در ثانیه حیاتی است |
| رویدادهای غیرهمزمان | **صف پیام (Kafka/NATS/RabbitMQ)** | وقتی سرویس A نیازی به جواب فوری از سرویس B ندارد (مثلاً «سفر تمام شد، حالا کیف‌پول را آپدیت کن»)، به‌جای صدا زدن مستقیم، یک پیام در صف می‌گذارد. اگر سرویس B موقتاً پایین باشد، پیام گم نمی‌شود — این «جفت‌نشدگی» (decoupling) باعث تاب‌آوری سیستم می‌شود |

**تأیید با شواهد واقعی:** بررسی مخازن گیت‌هاب رسمی اسنپ ([سند ۱۳](13-بررسی-مخازن-گیت‌هاب-رسمی-رقبا.md)) نشان داد اسنپ دقیقاً از NATS/MQTT (پیام‌رسانی) و Kubernetes استفاده می‌کند — این یک الگوی نظری نیست، شواهد مستقیم کد سازمانی آن‌هاست.

## ۳. جریان کامل یک درخواست واقعی — از کلاینت تا دیتابیس

نمونه: درخواست تاکسی (مسیر دیسپچ)

```
۱. مسافر روی «درخواست سفر» می‌زند (اپ React Native)
        ↓ HTTPS POST /api/rides
۲. API Gateway درخواست را می‌گیرد، توکن JWT را اعتبارسنجی می‌کند
        ↓ gRPC call
۳. سرویس دیسپچ (NestJS) درخواست را دریافت می‌کند
        ↓ Redis GEO query (نه HTTP، مستقیم به کش)
۴. نزدیک‌ترین رانندگان پیدا می‌شوند
        ↓ WebSocket push (اتصال زنده، نه REST)
۵. درخواست به گوشی راننده می‌رود
        ↓ راننده قبول می‌کند → WebSocket به مسافر برمی‌گردد
۶. سفر تمام می‌شود
        ↓ رویداد async به صف پیام فرستاده می‌شود: «ride.completed»
۷. سرویس پرداخت (Laravel) این رویداد را از صف می‌خواند
        ↓ کیف‌پول راننده را آپدیت می‌کند، کمیسیون را کسر می‌کند
        ↓ در PostgreSQL commit می‌شود (تراکنش اتمیک، با قفل‌گذاری ضد race-condition طبق سند ۱۰)
```

هر پیکان در این جریان، یک انتخاب فنی مستقل است — نه یک پروتکل واحد برای کل مسیر. این دقیقاً همان الگویی است که در پلتفرم‌های واقعی (اسنپ، Booking.com) نیز دیده می‌شود.

## ۴. لایه‌ی اضافه‌ی مخصوص رزرو (Booking Engine) — چیزی که در تاکسی نیست ولی در هتل/تور هست

پلتفرم‌های رزرو (بر خلاف تاکسی) یک لایه‌ی اضافه به نام **موتور رزرو (Booking Engine)** دارند که وظیفه‌اش:

1. **جستجو در چند تأمین‌کننده هم‌زمان** (چند هتل/آژانس)
2. **نرمال‌سازی داده** — چون هر هتل فرمت متفاوتی برای قیمت/ظرفیت دارد، این لایه همه را به یک مدل داخلی یکسان تبدیل می‌کند. این سخت‌ترین بخش مهندسی OTAهاست.
3. **Reprice و بررسی قوانین لغو**، درست پیش از تأیید نهایی رزرو
4. **ثبت رزرو با قفل‌گذاری** — همان راهکار race condition که در [سند ۱۰](10-معماری-فنی-MVP.md) بخش ۳.۱ طراحی شد

**تأمین‌کننده‌های معمول در OTAهای بزرگ:** بلیط پرواز از GDS (Amadeus, Sabre, Travelport) یا API مستقیم ایرلاین‌ها (NDC)؛ هتل از تجمیع‌کننده‌ها (Expedia Partner Solutions, Hotelbeds) یا اتصال مستقیم هتل؛ تجربه/جاذبه از تجمیع‌کننده‌های تخصصی مانند Viator یا Bokun.

**دلالت برای دلی:** سرویس «رزرو» (Laravel) باید از همان روز اول لایه‌ی نرمال‌سازی داده را داشته باشد، حتی اگر فاز ۱ فقط چند هتل قراردادی را دستی وارد کند — چون وقتی هتل بیشتری اضافه شود، این لایه از قبل آماده است و نیازی به بازطراحی نیست.

## ۵. جمع‌بندی — ورودی برای سند ۱۰

این سند لایه‌بندی و پروتکل‌های ارتباطی معماری تأییدشده‌ی [سند ۱۰](10-معماری-فنی-MVP.md) را با جزئیات بیشتر باز کرده است. نکات کلیدی برای پیاده‌سازی فاز ۱:
- ارتباط اپ↔بک‌اند: REST/HTTPS
- ارتباط NestJS↔Laravel (دو سرویس بک‌اند): gRPC یا API داخلی ساده در مقیاس MVP، با مسیر ارتقا به gRPC در مقیاس بزرگ‌تر
- رویدادهای غیرهمزمان (سفر تمام شد، رزرو ثبت شد): صف پیام Redis (کافی برای مقیاس پایلوت؛ ارتقا به Kafka/NATS در فاز ۴ در صورت نیاز)
- لایه‌ی نرمال‌سازی داده‌ی Booking باید از فاز ۱ در طراحی مدل داده لحاظ شود، نه فاز ۳
