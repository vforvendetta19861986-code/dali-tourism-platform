## ۲. اجزای اصلی و تصمیمات فناوری

### ۲.۱ اپ مسافر
**پیشنهاد: React Native** (نه PWA خالص) برای نسخه‌ی اصلی، به‌همراه یک **نسخه‌ی سبک PWA** موازی برای دسترسی سریع بدون نصب (مثلاً از طریق لینک هتل/فرودگاه).

**چرا نه فقط PWA:** رزرو تاکسی real-time (موقعیت زنده‌ی راننده، اعلان فوری) روی PWA در مرورگرهای موبایل ایران (به‌ویژه iOS Safari) محدودیت push notification و GPS پس‌زمینه داره. برای تجربه‌ی رقابتی در برابر اسنپ/تپسی (که هر دو اپ نیتیو دارن)، اپ نیتیو ضروریه.

**قابلیت‌های فاز ۱:**
- ثبت‌نام/ورود (شماره موبایل + OTP)
- درخواست سفر (نقطه‌ی مبدأ/مقصد روی نقشه)
- نمایش موقعیت زنده‌ی راننده
- پرداخت (کیف‌پول داخلی + درگاه)
- سبد سفر ساده (نمایش لیست هتل/تور/رستوران قراردادی مشهد — فقط نمایش و رزرو ساده، نه موتور پیشنهاددهنده‌ی پیچیده)
- تاریخچه‌ی سفر و امتیازدهی

### ۲.۲ اپ راننده
**پیشنهاد: React Native** (اشتراک کد بالا با اپ مسافر از طریق کتابخانه‌های مشترک).

**قابلیت‌های فاز ۱:**
- پذیرش/رد درخواست سفر
- مسیریابی به مقصد
- ثبت وضعیت سفر (شروع/پایان)
- گزارش درآمد روزانه/ماهانه
- پروفایل و مدارک (آپلود بیمه، معاینه فنی — طبق [سند ۰۳](03-مجوزها-و-مدارک-پرونده-بانکی.md))

### ۲.۳ پنل مدیریت (Admin)
**پیشنهاد: Next.js** (وب، نه اپ موبایل).

**قابلیت‌های فاز ۱:**
- دیسپچ و نظارت زنده بر سفرهای در حال انجام
- مدیریت راننده و خودرو (تأیید مدارک، فعال/غیرفعال کردن)
- مدیریت عرضه‌کنندگان (هتل/تور/رستوران قراردادی)
- گزارش KPI (طبق فاز ۲ نقشه راه: توان بازپرداخت، رضایت مشتری، نرخ تکمیل سفر)
- مدیریت نرخ کمیسیون (قابل‌تغییر بدون نیاز به دیپلوی مجدد — چون طبق [سند ۰۵](05-مدل-درآمدی-و-تعرفه‌گذاری.md) نرخ تاکسی قراره از ۱۲٪ به ۱۵٪ تغییر کنه)

### ۲.۴ پنل B2B (عرضه‌کننده)
در فاز ۱ نسخه‌ی حداقلی (حتی می‌تواند بخشی از پنل مدیریت با نقش محدود باشد)؛ توسعه‌ی کامل طبق نقشه راه در فاز ۳ است.

### ۲.۵ بک‌اند
**پیشنهاد: Node.js + NestJS (TypeScript)**

**چرا:** تایپ‌اسکریپت مشترک بین بک‌اند و React Native/Next.js (کاهش خطای type mismatch بین لایه‌ها)، اکوسیستم بزرگ برای real-time (WebSocket) و صف پیام (job queue برای دیسپچ).

**ماژول‌های اصلی:**
- Auth (OTP، JWT)
- Rides (درخواست، دیسپچ، وضعیت سفر)
- Drivers / Vehicles
- Bookings (هتل/تور/رستوران ساده)
- Payments (کیف‌پول، تسویه‌حساب با عرضه‌کننده طبق نرخ کمیسیون)
- Admin/Reporting

### ۲.۶ دیتابیس
**پیشنهاد: PostgreSQL** (رابطه‌ای، برای یکپارچگی تراکنش‌های مالی/رزرو) + **Redis** (کش، صف پیام، موقعیت زنده‌ی راننده).

### ۲.۷ نقشه و موقعیت‌یابی
**پیشنهاد: نشان (Neshan) یا بلد (Balad)** — نه Google Maps.

**چرا:** به‌دلیل محدودیت‌های تحریمی و دقت پایین‌تر Google Maps برای آدرس‌دهی داخل ایران، هر دو رقیب اصلی (اسنپ، تپسی) از نقشه‌های داخلی استفاده می‌کنند. نشان API مسیریابی، ژئوکدینگ و نمایش نقشه‌ی بومی مشهد را پوشش می‌دهد.

### ۲.۸ درگاه پرداخت
**پیشنهاد: زرین‌پال** (یا آیدی‌پی به‌عنوان جایگزین) — درگاه پرداخت داخلی استاندارد صنعت، سازگار با شتاب.

### ۲.۹ پیامک/اعلان
سرویس پیامک داخلی (مثل کاوه‌نگار یا ملی‌پیامک) برای OTP و اطلاع‌رسانی سفر؛ Push Notification از طریق Firebase Cloud Messaging (در دسترس‌بودنش در ایران باید تست شود؛ در صورت محدودیت، جایگزین داخلی مثل نوتیفای بررسی شود).

## ۳. مدل داده‌ی هسته (Core Entities)

```
User (مسافر)
  ├─ id, phone, name, wallet_balance
  └─ rides[], bookings[]

Driver (راننده)
  ├─ id, phone, name, license_status, insurance_status
  └─ vehicle, rides[]

Vehicle (خودرو)
  ├─ id, plate_number, model, capacity, inspection_expiry
  └─ driver

Ride (سفر)
  ├─ id, user_id, driver_id, origin, destination, status
  ├─ fare, commission_rate (۱۲٪ یا ۱۵٪ — قابل‌تغییر در زمان)
  └─ payment

Supplier (عرضه‌کننده: هتل/تور/رستوران)
  ├─ id, type (hotel|tour|restaurant), name, contract_commission_rate
  └─ listings[]

Booking (رزرو سبد سفر)
  ├─ id, user_id, supplier_id, listing_id, status
  └─ payment

Payment (تراکنش)
  ├─ id, amount, type (ride|booking), gateway_ref, status
  └─ commission_amount, supplier_payout_amount
```

**نکته‌ی طراحی مهم:** فیلد `commission_rate` باید **در سطح تراکنش ثبت بشه، نه فقط سطح تنظیمات کلی** — چون طبق تصمیم نهایی‌شده (نرخ تاکسی از ۱۲٪ به ۱۵٪ در آینده تغییر می‌کنه)، باید بشه تاریخچه‌ی نرخ هر تراکنش رو حفظ کرد، نه اینکه با تغییر نرخ کلی، محاسبه‌ی تراکنش‌های قدیمی هم عوض بشه.

## ۴. زیرساخت و میزبانی

**ملاحظه‌ی مهم:** به‌دلیل تحریم‌ها، سرویس‌های ابری بین‌المللی (AWS، GCP، Azure) برای شرکت‌های ایرانی معمولاً در دسترس نیستند یا پرریسک‌اند.

**پیشنهاد:** میزبانی روی ابر داخلی ایرانی (مانند ابر آروان — ArvanCloud، یا پردازش ابری افرانت) که CDN، دیتابیس مدیریت‌شده و Object Storage داخلی ارائه می‌دهند و تجربه‌ی مشابه AWS/GCP دارند.

**امنیت:** طبق سند دوم پروپوزال («امنیت، داده و حریم خصوصی») — حداقل‌گرایی داده، رمزنگاری اطلاعات پرداخت/هویتی، کنترل دسترسی نقش‌محور برای کارکنان.

## ۵. جریان کلی یک سفر (Ride Flow) — نمونه

```
مسافر درخواست سفر می‌دهد
        │
        ▼
بک‌اند نزدیک‌ترین رانندگان فعال را پیدا می‌کند (Redis geo-query)
        │
        ▼
درخواست به رانندگان ارسال می‌شود (WebSocket push)
        │
        ▼
راننده قبول می‌کند → مسافر مطلع می‌شود (موقعیت زنده‌ی راننده)
        │
        ▼
سفر انجام می‌شود → راننده وضعیت را "پایان‌یافته" ثبت می‌کند
        │
        ▼
محاسبه‌ی کرایه + کسر کمیسیون (۱۲٪ در فاز پایلوت) → تسویه با راننده
        │
        ▼
درخواست امتیازدهی از مسافر
```

## ۶. آنچه در فاز ۱ ساخته **نمی‌شود** (به‌عمد، طبق فازبندی نقشه راه)

- موتور «سبد سفر / سفر من را بساز» پیچیده (فاز ۳)
- پنل B2B کامل با API عمومی (فاز ۳)
- اتصال بلیط هواپیما/اتوبوس (فاز ۳، از طریق ریسلر)
- زیرساخت چندشهری/چندزبانه (فاز ۴ و ۵)
- ماژول گردشگری سلامت (فاز ۵)

این محدودسازی عمدی، دقیقاً همان درسی است که در [سند ۰۱](01-تحلیل-الگوهای-موفق-و-ناموفق.md) از شکست‌های سوپراپ ناشی از گسترش هم‌زمان گرفته شد.

## ۷. جمع‌بندی پشته‌ی فناوری (Tech Stack)

| لایه | فناوری |
|---|---|
| اپ مسافر/راننده | React Native (TypeScript) |

| بک‌اند | Node.js + NestJS (TypeScript) |

| پیامک | کاوه‌نگار یا ملی‌پیامک |
