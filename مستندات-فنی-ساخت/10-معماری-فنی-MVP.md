# معماری فنی MVP — فاز ۱ (ساخت اپلیکیشن مشهد)

**پروژه:** دلی (DALI) — پلتفرم جامع خدمات و تجربه گردشگری + شبکه تاکسی گردشگری
**تاریخ تدوین:** ۱۴۰۵/۰۶/۱۰ (۱ سپتامبر ۲۰۲۶)
**هدف سند:** طراحی معماری فنی MVP برای فاز ۱ نقشه راه ([سند ۰۸](08-برنامه-اجرایی-کامل.md)) — تاکسی گردشگری + سبد سفر ساده در مشهد. این سند فقط طراحیه؛ هیچ کدی نوشته نشده است.

> **وضعیت: ✅ تأیید شده توسط کارفرما (۱۴۰۵/۰۶/۱۰).** نسخه‌ی دوم بازبینی، بر پایه‌ی [سند ۱۱](11-بررسی-تکنولوژی-رقبا-و-چالش‌های-فنی.md) و [سند ۱۲](12-حوادث-امنیتی-واقعی-و-درس‌های-هاردنینگ.md). تغییرات نسخه‌ی اول به دوم: (۱) بک‌اند از تک‌فناوری NestJS به مدل ترکیبی (NestJS برای دیسپچ real-time + PHP/Laravel برای رزرو/مدیریت) تغییر کرد؛ (۲) طراحی صریح قفل‌گذاری برای race condition اضافه شد؛ (۳) بودجه‌ی امنیتی/باگ‌بانتی به فاز ۱ اضافه شد؛ (۴) مدیریت خطای GPS و صف پیام برای دیسپچ مشخص شد. تغییرات نسخه‌ی دوم (بر پایه‌ی حوادث واقعی هک اسنپ‌فود و علی‌بابا): (۵) استاندارد هش پسورد (bcrypt/argon2) به‌صراحت در مدل داده اضافه شد؛ (۶) سیاست عدم ذخیره‌ی داده‌ی پرداخت، امنیت مخزن کد، و برنامه‌ی واکنش به حادثه مشخص شد. این معماری مبنای شروع فاز ۱ (ساخت واقعی MVP، طبق [سند ۰۸](08-برنامه-اجرایی-کامل.md)) است.

## ۲. اجزای اصلی و تصمیمات فناوری

### ۲.۱ اپ مسافر
**پیشنهاد: React Native** (نه PWA خالص) برای نسخه‌ی اصلی، به‌همراه یک **نسخه‌ی سبک PWA** موازی برای دسترسی سریع بدون نصب (مثلاً از طریق لینک هتل/فرودگاه).

**چرا نه فقط PWA:** رزرو تاکسی real-time (موقعیت زنده‌ی راننده، اعلان فوری) روی PWA در مرورگرهای موبایل ایران (به‌ویژه iOS Safari) محدودیت push notification و GPS پس‌زمینه داره. برای تجربه‌ی رقابتی در برابر اسنپ/تپسی (که هر دو اپ نیتیو دارن)، اپ نیتیو ضروریه.

**قابلیت‌های فاز ۱:**
- ثبت‌نام/ورود (شماره موبایل + OTP)
- درخواست سفر (نقطه‌ی مبدأ/مقصد روی نقشه)
- نمایش موقعیت زنده‌ی راننده
- پرداخت (کیف‌پول داخلی + درگاه)
- سبد سفر ساده (نمایش لیست هتل/تور/رستوران قراردادی مشهد — فقط نمایش و رزرو ساده، نه موتور پیشنهاددهنده‌ی پیچیده)
- تاریخچه‌ی سفر و امتیازدهی

### ۲.۲ اپ راننده
**پیشنهاد: React Native** (اشتراک کد بالا با اپ مسافر از طریق کتابخانه‌های مشترک).

**قابلیت‌های فاز ۱:**
- پذیرش/رد درخواست سفر
- مسیریابی به مقصد
- ثبت وضعیت سفر (شروع/پایان)
- گزارش درآمد روزانه/ماهانه
- پروفایل و مدارک (آپلود بیمه، معاینه فنی — طبق [سند ۰۳](03-مجوزها-و-مدارک-پرونده-بانکی.md))

### ۲.۳ پنل مدیریت (Admin)
**پیشنهاد: Next.js** (وب، نه اپ موبایل).

**قابلیت‌های فاز ۱:**
- دیسپچ و نظارت زنده بر سفرهای در حال انجام
- مدیریت راننده و خودرو (تأیید مدارک، فعال/غیرفعال کردن)
- مدیریت عرضه‌کنندگان (هتل/تور/رستوران قراردادی)
- گزارش KPI (طبق فاز ۲ نقشه راه: توان بازپرداخت، رضایت مشتری، نرخ تکمیل سفر)
- مدیریت نرخ کمیسیون (قابل‌تغییر بدون نیاز به دیپلوی مجدد — چون طبق [سند ۰۵](05-مدل-درآمدی-و-تعرفه‌گذاری.md) نرخ تاکسی قراره از ۱۲٪ به ۱۵٪ تغییر کنه)

### ۲.۴ پنل B2B (عرضه‌کننده)
در فاز ۱ نسخه‌ی حداقلی (حتی می‌تواند بخشی از پنل مدیریت با نقش محدود باشد)؛ توسعه‌ی کامل طبق نقشه راه در فاز ۳ است.

### ۲.۵ بک‌اند — مدل ترکیبی (بازبینی‌شده طبق سند ۱۱)

**سرویس ۱ — دیسپچ real-time: Node.js + NestJS (TypeScript)**
مسئول درخواست سفر، تطبیق راننده-مسافر، موقعیت زنده، WebSocket. تایپ‌اسکریپت مشترک با React Native/Next.js لایه‌های دیگر را ساده می‌کند؛ اکوسیستم قوی برای WebSocket و صف پیام (job queue).

**سرویس ۲ — رزرو و مدیریت: PHP/Laravel**
مسئول ماژول‌های کمتر latency-حساس: مدیریت عرضه‌کننده (هتل/تور/رستوران)، رزرو سبد سفر، Auth، Admin/Reporting، Payments. توسعه‌ی سریع‌تر با Laravel (ORM قوی، ابزار Admin آماده)، و دسترسی آسان‌تر به نیروی متخصص PHP در بازار کار ایران — طبق [سند ۱۱](11-بررسی-تکنولوژی-رقبا-و-چالش‌های-فنی.md)، دقیقاً همان الگوی Doctoreto.

**تقسیم ماژول‌ها:**

| ماژول | سرویس | دلیل |
|---|---|---|
| Rides (درخواست، دیسپچ، وضعیت زنده) | NestJS | latency-حساس، WebSocket |
| Drivers/Vehicles (موقعیت زنده) | NestJS | نیازمند geo-query سریع |
| Auth (OTP, JWT) | Laravel | CRUD ساده، نیاز به سرعت توسعه |
| Bookings (هتل/تور/رستوران) | Laravel | منطق تجاری، نه latency-حساس |
| Payments (کیف‌پول، تسویه) | Laravel | تراکنش مالی، ORM قوی برای یکپارچگی |
| Admin/Reporting | Laravel | ابزار Admin آماده در اکوسیستم Laravel |

هر دو سرویس به یک دیتابیس PostgreSQL مشترک متصل می‌شوند و از طریق API داخلی (یا صف پیام Redis برای رویدادهای غیرهمزمان، مثل «سفر تمام شد → به‌روزرسانی کیف‌پول») با هم ارتباط دارند.

### ۲.۶ دیتابیس
**پیشنهاد: PostgreSQL** (رابطه‌ای، برای یکپارچگی تراکنش‌های مالی/رزرو) + **Redis** (کش، صف پیام، موقعیت زنده‌ی راننده).

### ۲.۷ نقشه و موقعیت‌یابی
**پیشنهاد: نشان (Neshan) یا بلد (Balad)** — نه Google Maps.

**چرا:** به‌دلیل محدودیت‌های تحریمی و دقت پایین‌تر Google Maps برای آدرس‌دهی داخل ایران، هر دو رقیب اصلی (اسنپ، تپسی) از نقشه‌های داخلی استفاده می‌کنند. نشان API مسیریابی، ژئوکدینگ و نمایش نقشه‌ی بومی مشهد را پوشش می‌دهد.

### ۲.۸ درگاه پرداخت
**پیشنهاد: زرین‌پال** (یا آیدی‌پی به‌عنوان جایگزین) — درگاه پرداخت داخلی استاندارد صنعت، سازگار با شتاب.

### ۲.۹ پیامک/اعلان
سرویس پیامک داخلی (مثل کاوه‌نگار یا ملی‌پیامک) برای OTP و اطلاع‌رسانی سفر؛ Push Notification از طریق Firebase Cloud Messaging (در دسترس‌بودنش در ایران باید تست شود؛ در صورت محدودیت، جایگزین داخلی مثل نوتیفای بررسی شود).

## ۳. مدل داده‌ی هسته (Core Entities)

```
User (مسافر)
  ├─ id, phone, name, password_hash (bcrypt/argon2 — نه هرگز plaintext یا MD5/SHA1)
  ├─ wallet_balance
  └─ rides[], bookings[]

Driver (راننده)
  ├─ id, phone, name, password_hash (bcrypt/argon2)
  ├─ license_status, insurance_status
  └─ vehicle, rides[]

Vehicle (خودرو)
  ├─ id, plate_number, model, capacity, inspection_expiry
  └─ driver

Ride (سفر)
  ├─ id, user_id, driver_id, origin, destination, status
  ├─ fare, commission_rate (۱۲٪ یا ۱۵٪ — قابل‌تغییر در زمان)
  └─ payment

Supplier (عرضه‌کننده: هتل/تور/رستوران)
  ├─ id, type (hotel|tour|restaurant), name, contract_commission_rate
  └─ listings[]

Booking (رزرو سبد سفر)
  ├─ id, user_id, supplier_id, listing_id, status
  └─ payment

Payment (تراکنش)
  ├─ id, amount, type (ride|booking), gateway_ref, status
  └─ commission_amount, supplier_payout_amount
```

**نکته‌ی طراحی مهم:** فیلد `commission_rate` باید **در سطح تراکنش ثبت بشه، نه فقط سطح تنظیمات کلی** — چون طبق تصمیم نهایی‌شده (نرخ تاکسی از ۱۲٪ به ۱۵٪ در آینده تغییر می‌کنه)، باید بشه تاریخچه‌ی نرخ هر تراکنش رو حفظ کرد، نه اینکه با تغییر نرخ کلی، محاسبه‌ی تراکنش‌های قدیمی هم عوض بشه.

### ۳.۱ جلوگیری از Race Condition در Booking (اضافه‌شده طبق سند ۱۱)

طبق یافته‌ی [سند ۱۱](11-بررسی-تکنولوژی-رقبا-و-چالش‌های-فنی.md)، double-booking (دو مسافر هم‌زمان یک اتاق هتل یا صندلی تور را رزرو می‌کنند) در تست محلی دیده نمی‌شود و فقط زیر ترافیک واقعی خود را نشان می‌دهد. برای جلوگیری، جدول `Booking` باید از ابتدا با یکی از دو روش زیر پیاده‌سازی شود، نه بعداً اضافه شود:

- **قفل‌گذاری بدبینانه (Pessimistic Locking):** در لحظه‌ی شروع فرآیند رزرو، سطر «موجودی» (ظرفیت اتاق/صندلی) در دیتابیس قفل می‌شود تا تراکنش تمام شود (`SELECT ... FOR UPDATE` در PostgreSQL).
- **قفل‌گذاری خوش‌بینانه (Optimistic Locking):** هر رکورد موجودی یک فیلد `version` دارد؛ به‌روزرسانی فقط وقتی موفق می‌شود که نسخه‌ی خوانده‌شده هنوز معتبر باشد؛ در غیر این صورت رزرو رد و به کاربر اطلاع داده می‌شود.

**تصمیم برای فاز ۱:** با توجه به حجم پایین تراکنش‌های همزمان پایلوت (تعداد محدود هتل/رستوران قراردادی)، قفل‌گذاری بدبینانه ساده‌تر و کافی است؛ در فاز‌های بعدی با افزایش ترافیک، بازبینی به سمت قفل‌گذاری خوش‌بینانه در نظر گرفته شود.

## ۴. زیرساخت و میزبانی

**ملاحظه‌ی مهم:** به‌دلیل تحریم‌ها، سرویس‌های ابری بین‌المللی (AWS، GCP، Azure) برای شرکت‌های ایرانی معمولاً در دسترس نیستند یا پرریسک‌اند.

**پیشنهاد:** میزبانی روی ابر داخلی ایرانی (مانند ابر آروان — ArvanCloud، یا پردازش ابری افرانت) که CDN، دیتابیس مدیریت‌شده و Object Storage داخلی ارائه می‌دهند و تجربه‌ی مشابه AWS/GCP دارند.

**امنیت:** طبق سند دوم پروپوزال («امنیت، داده و حریم خصوصی») — حداقل‌گرایی داده، رمزنگاری اطلاعات پرداخت/هویتی، کنترل دسترسی نقش‌محور برای کارکنان.

**بودجه‌ی امنیتی از فاز ۱ (اضافه‌شده طبق سند ۱۱):** طبق یافته‌ی برنامه‌ی باگ‌بانتی اسنپ (پاداش تا ۳۰۰ میلیون تومان برای باگ حیاتی، ۸۰ باگ کشف‌شده طی سال‌ها)، حتی پلتفرم‌های بالغ دائماً آسیب‌پذیری پیدا می‌کنند. برای دلی در فاز ۱ توصیه می‌شود:
- تست نفوذ (Penetration Test) پیش از راه‌اندازی پایلوت
- برنامه‌ی افشای مسئولانه‌ی غیررسمی (حتی بدون پاداش مالی بزرگ، یک کانال گزارش آسیب‌پذیری)
- این بودجه باید در برآورد هزینه‌ی MVP (۱ تا ۲ میلیارد تومان، طبق سند پروپوزال) به‌صراحت لحاظ شود، نه بعد از حادثه اضافه شود.

**اقدامات هاردنینگ ملموس (اضافه‌شده طبق [سند ۱۲- حوادث امنیتی واقعی و درس‌های هاردنینگ](12-حوادث-امنیتی-واقعی-و-درس‌های-هاردنینگ.md)، بر پایه‌ی حوادث واقعی هک اسنپ‌فود و علی‌بابا):**
- **هش پسورد:** الزامی با bcrypt یا argon2 برای فیلدهای `password_hash` در User/Driver — هرگز plaintext یا MD5/SHA1 (طبق درس نشت پسورد در هک اسنپ‌فود)
- **عدم ذخیره‌ی داده‌ی پرداخت:** دلی هرگز شماره کامل کارت/CVV را در دیتابیس خودش ذخیره نمی‌کند؛ تمام پرداخت‌ها فقط از طریق توکن درگاه (زرین‌پال) — همان الگویی که باعث شد داده‌ی پرداخت در هک اسنپ‌فود امن بماند
- **امنیت مخزن کد:** مخزن Git **private**، مدیریت اسرار (API key، رمز دیتابیس) از طریق Vault/متغیر محیطی — هرگز هاردکد در کد؛ اسکن خودکار secret leak در CI/CD (طبق درس سرقت سورس‌کد در هک علی‌بابا)
- **برنامه‌ی واکنش به حادثه (Incident Response):** یک سند مکتوب (نه چیزی که در لحظه‌ی بحران بداهه‌سازی شود) شامل مراحل تشخیص، مهار، اطلاع‌رسانی شفاف به کاربران — طبق الگوی مثبت ارزیابی‌شده‌ی شفافیت علی‌بابا پس از حادثه‌اش
- **پایش تهدید مداوم، نه فقط یک تست نفوذ یک‌باره:** الگوی حمله‌ی گروه IRLeaks (تپسی ← اسنپ‌فود) نشان می‌دهد این رده از پلتفرم‌ها هدف تکرارشونده‌اند

## ۵. جریان کلی یک سفر (Ride Flow) — نمونه

```
مسافر درخواست سفر می‌دهد
        │
        ▼
بک‌اند (NestJS) نزدیک‌ترین رانندگان فعال را پیدا می‌کند (Redis geo-query)
        │
        ▼
درخواست به رانندگان ارسال می‌شود (WebSocket push، از طریق صف پیام Redis
تا در صورت قطعی موقت اتصال راننده، درخواست از دست نرود)
        │
        ▼
راننده قبول می‌کند → مسافر مطلع می‌شود (موقعیت زنده‌ی راننده)
        │
        ▼
سفر انجام می‌شود → راننده وضعیت را "پایان‌یافته" ثبت می‌کند
        │
        ▼
رویداد "سفر تمام شد" به سرویس Laravel ارسال می‌شود (صف پیام)
محاسبه‌ی کرایه + کسر کمیسیون (۱۲٪ در فاز پایلوت) → تسویه با راننده
        │
        ▼
درخواست امتیازدهی از مسافر
```

**مدیریت خطای GPS (اضافه‌شده طبق سند ۱۱):** طبق یافته‌ی سند ۱۱، دقت GPS به دستگاه و موقعیت وابسته است. طراحی باید فرض عدم‌دقت را از ابتدا بپذیرد:
- فیلتر میانگین متحرک (moving average) روی مختصات دریافتی برای کاهش پرش‌های ناگهانی موقعیت
- آستانه‌ی حداقل دقت (accuracy radius) قبل از پذیرش یک بروزرسانی موقعیت
- Fallback به آخرین موقعیت معتبر در صورت دریافت داده‌ی نامعتبر، به‌جای نمایش موقعیت اشتباه به مسافر

## ۶. آنچه در فاز ۱ ساخته **نمی‌شود** (به‌عمد، طبق فازبندی نقشه راه)

- موتور «سبد سفر / سفر من را بساز» پیچیده (فاز ۳)
- پنل B2B کامل با API عمومی (فاز ۳)
- اتصال بلیط هواپیما/اتوبوس (فاز ۳، از طریق ریسلر)
- زیرساخت چندشهری/چندزبانه (فاز ۴ و ۵)
- ماژول گردشگری سلامت (فاز ۵)

این محدودسازی عمدی، دقیقاً همان درسی است که در [سند ۰۱](01-تحلیل-الگوهای-موفق-و-ناموفق.md) از شکست‌های سوپراپ ناشی از گسترش هم‌زمان گرفته شد.
