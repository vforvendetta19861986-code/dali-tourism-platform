**پروژه:** دلی (DALI) — پلتفرم جامع خدمات و تجربه گردشگری + شبکه تاکسی گردشگری
**تاریخ تدوین:** ۱۴۰۵/۰۶/۱۱ (۲ سپتامبر ۲۰۲۶)
**هدف سند:** برخلاف [سند ۰۸](08-برنامه-اجرایی-کامل.md) (نقشه راه کسب‌وکاری کل پروژه) و [سند ۱۰](10-معماری-فنی-MVP.md) (چیستی معماری)، این سند مشخصاً **چگونگی ساخت نرم‌افزار** را باز می‌کند: الگوریتم‌های هسته، فازبندی مهندسی نرم‌افزار (نه فازبندی کسب‌وکاری)، و چک‌لیست کامل زیرساخت. مبتنی بر تصمیمات نهایی‌شده در اسناد ۱۰، ۱۱، ۱۲، ۱۳، ۱۵.

## ۱. الگوریتم‌های هسته‌ی نرم‌افزار

### ۱.۱ الگوریتم دیسپچ (تطبیق راننده-مسافر)

```
ورودی: موقعیت مسافر (lat, lng)
۱. جست‌وجوی geo-radius در Redis برای رانندگان «فعال و آزاد» در شعاع اولیه (مثلاً ۳ کیلومتر)
۲. اگر راننده‌ای پیدا نشد → افزایش شعاع جست‌وجو (۳ → ۵ → ۸ کیلومتر) تا سقف مشخص
۳. فیلتر رانندگان یافت‌شده بر اساس: نوع خودرو درخواستی، امتیاز حداقلی، وضعیت مدارک (بیمه/معاینه فنی معتبر — طبق سند ۰۳)
۴. رتبه‌بندی بر اساس ترکیب «نزدیک‌ترین زمان رسیدن» + «امتیاز راننده» (نه فقط نزدیک‌ترین فاصله‌ی خطی)
۵. ارسال درخواست به بهترین گزینه با timeout کوتاه (مثلاً ۱۵ ثانیه)
۶. اگر رد شد یا timeout شد → برو به گزینه‌ی بعدی در رتبه‌بندی (نه جست‌وجوی مجدد از صفر)
خروجی: تخصیص سفر یا اعلام «رانندهی در دسترس نیست»
```

**نکته‌ی طراحی مهم:** این الگوریتم باید idempotent باشد — یعنی اگر به‌خاطر خطای شبکه دوبار اجرا شود، دو راننده هم‌زمان به یک مسافر تخصیص داده نشوند (قفل توزیع‌شده‌ی Redis روی شناسه‌ی درخواست سفر).

### ۱.۲ الگوریتم رزرو (جلوگیری از Double-Booking)

```
ورودی: درخواست رزرو (supplier_id, listing_id, تاریخ)
۱. شروع تراکنش دیتابیس
۲. SELECT ... FOR UPDATE روی سطر موجودی (قفل بدبینانه — طبق سند ۱۰ بخش ۳.۱)
۳. بررسی موجودی واقعی در لحظه (نه موجودی کش‌شده)
۴. اگر موجودی کافی: کسر موجودی + ثبت رزرو + commit
۵. اگر موجودی ناکافی: rollback + پیام «ظرفیت تکمیل شد» به کاربر
خروجی: رزرو تأییدشده یا رد رزرو با دلیل شفاف
```

### ۱.۳ الگوریتم محاسبه‌ی کمیسیون و تسویه

```
ورودی: تراکنش تکمیل‌شده (نوع: ride/hotel/restaurant/tour/ticket)
۱. واکشی نرخ کمیسیون معتبر در لحظه‌ی تراکنش (نه نرخ فعلی سیستم — طبق سند ۱۰: commission_rate باید در سطح تراکنش ذخیره شود)
۲. محاسبه: مبلغ_کمیسیون = مبلغ_کل × نرخ
۳. محاسبه: مبلغ_تسویه_عرضه‌کننده = مبلغ_کل − مبلغ_کمیسیون
۴. ثبت هر دو مبلغ در جدول Payment (نه فقط مبلغ نهایی — برای گزارش‌گیری و حسابرسی)
۵. رویداد "payment.settled" به صف پیام برای به‌روزرسانی کیف‌پول ارسال می‌شود
خروجی: تسویه‌حساب ثبت‌شده و قابل رهگیری
```

## ۲. فازبندی مهندسی نرم‌افزار (Sprint-Level) — تفصیل فاز ۱ نقشه راه کسب‌وکاری

[سند ۰۸](08-برنامه-اجرایی-کامل.md) فاز ۱ را در ۷ وظیفه‌ی کلی و ۴ تا ۶ ماه خلاصه کرده بود. این بخش آن را به اسپرینت‌های عملیاتی می‌شکند:

| اسپرینت | محتوا | خروجی قابل‌نمایش | وابستگی |
|---|---|---|---|
| **۰ (آماده‌سازی)** | راه‌اندازی مخزن Git، CI/CD پایه، محیط‌های dev/staging، مدیریت اسرار (SOPS+age طبق سند ۱۳) | پروژه‌ی خالی ولی قابل‌دیپلوی | تیم فنی استخدام شده |
| **۱-۲ (هسته‌ی داده و Auth)** | مدل داده‌ی هسته (سند ۱۰ بخش ۳)، احراز هویت OTP، ساختار دو سرویس بک‌اند (NestJS + Laravel) | API‌های پایه، لاگین کار می‌کند | اسپرینت ۰ |
| **۳-۴ (دیسپچ)** | پیاده‌سازی الگوریتم دیسپچ (بخش ۱.۱ همین سند)، WebSocket، Redis geo | درخواست سفر و تخصیص راننده در محیط تست کار می‌کند | اسپرینت ۱-۲ |
| **۵-۶ (اپ‌های کلاینت)** | اپ مسافر و راننده (React Native) متصل به بک‌اند | نسخه‌ی نصب‌شدنی روی گوشی واقعی | اسپرینت ۳-۴ |
| **۷-۸ (پرداخت و رزرو ساده)** | اتصال زرین‌پال، الگوریتم رزرو (بخش ۱.۲)، الگوریتم تسویه (بخش ۱.۳) | تراکنش end-to-end کامل، از درخواست سفر تا تسویه | اسپرینت ۵-۶ |
| **۹-۱۰ (پنل مدیریت و QA)** | پنل مدیریت (Next.js)، تست امنیتی اولیه (طبق سند ۱۲)، رفع باگ | نسخه‌ی آماده‌ی پایلوت روی ۱۰ خودروی آزمایشی | اسپرینت ۷-۸ |

هر اسپرینت ~۲ تا ۳ هفته در نظر گرفته می‌شود؛ مجموع ۱۰ اسپرینت با فاصله‌ی بافر، همان ۴ تا ۶ ماه فاز ۱ سند ۰۸ را پوشش می‌دهد.

**معیار خروج هر اسپرینت:** دمو زنده و قابل‌اجرا در محیط staging — نه فقط کد merge‌شده.

## ۳. چک‌لیست کامل زیرساخت مورد نیاز

### ۳.۱ محیط‌های اجرا
- [ ] محیط **Development** (تیم فنی، دیتای تستی)
- [ ] محیط **Staging** (شبیه‌سازی production، برای تست پیش از انتشار)
- [ ] محیط **Production** (کاربران واقعی پایلوت مشهد)

### ۳.۲ زیرساخت ابری (طبق سند ۱۰)
- [ ] حساب ابر آروان (ArvanCloud) یا معادل داخلی
- [ ] سرور/کانتینر برای سرویس NestJS (دیسپچ)
- [ ] سرور/کانتینر برای سرویس Laravel (رزرو/مدیریت/پرداخت)
- [ ] نمونه‌ی PostgreSQL مدیریت‌شده (با پشتیبان‌گیری خودکار روزانه)
- [ ] نمونه‌ی Redis (کش + geo-query + صف پیام)
- [ ] Object Storage برای تصاویر (پروفایل راننده، مدارک، تصاویر هتل/رستوران)
- [ ] CDN برای تحویل سریع تصاویر و فایل‌های استاتیک

### ۳.۳ دامنه و شبکه
- [ ] ثبت دامنه‌ی رسمی (`dali.ir` یا معادل)
- [ ] گواهی SSL/TLS (Let's Encrypt یا معادل)
- [ ] پیکربندی DNS
- [ ] Load Balancer (حتی در فاز ۱ برای آماده‌بودن مسیر مقیاس‌پذیری)

### ۳.۴ CI/CD و DevOps
- [ ] Pipeline خودکار build/test/deploy (GitHub Actions یا معادل)
- [ ] مدیریت اسرار با **SOPS + age** (طبق سند ۱۳)
- [ ] اسکن خودکار secret leak در هر commit (طبق سند ۱۲)
- [ ] مخزن Git **private**

### ۳.۵ مانیتورینگ و لاگ
- [ ] سیستم لاگ متمرکز (حداقل برای خطاهای production)
- [ ] پایش uptime/کارایی سرویس‌های حیاتی (دیسپچ، پرداخت)
- [ ] هشدار خودکار (Alert) برای خرابی سرویس

### ۳.۶ سرویس‌های بیرونی (طبق سند ۱۰)
- [ ] قرارداد و کلید API درگاه پرداخت (زرین‌پال)
- [ ] قرارداد و کلید API نقشه (نشان/بلد)
- [ ] قرارداد سرویس پیامک (کاوه‌نگار/ملی‌پیامک) برای OTP
- [ ] بررسی دسترسی Firebase Cloud Messaging در ایران؛ آماده‌سازی جایگزین داخلی در صورت محدودیت

### ۳.۷ امنیت (طبق سند ۱۲)
- [ ] هش پسورد با bcrypt/argon2 از روز اول کدنویسی
- [ ] تست نفوذ پیش از راه‌اندازی پایلوت
- [ ] کانال گزارش آسیب‌پذیری (حتی غیررسمی)
- [ ] برنامه‌ی مکتوب واکنش به حادثه

### ۳.۸ تیم و ابزار همکاری
- [ ] ابزار مدیریت پروژه/تسک (برای پیگیری اسپرینت‌ها)
- [ ] کانال ارتباطی تیم فنی
- [ ] مستندسازی API داخلی (برای هماهنگی دو سرویس NestJS/Laravel)

## ۴. جمع‌بندی

این سند، لایه‌ی «چگونه» را روی لایه‌ی «چه چیزی» (سند ۱۰) و لایه‌ی «چه زمانی در کسب‌وکار» (سند ۰۸) اضافه می‌کند. سه الگوریتم هسته (دیسپچ، رزرو، تسویه) باید در همان اسپرینت‌های ۳ تا ۸ به‌طور کامل و با تست پیاده‌سازی شوند — این‌ها قلب تپنده‌ی MVP هستند، نه ویژگی‌های جانبی.
